# ADR-017: Organization control plane and configurable operational permissions

Status: CURRENT for #105 implementation foundation. Recorded 2026-09-22 under explicit owner direction. This ADR defines authorization architecture and control-plane UX; it does not authorize production promotion.

## Problem

The POS currently has only operational location roles `cashier` and `manager`, with permissions hard-coded in `server/auth/roles.ts`. A manager signs into the same cashier-oriented shell, there is no first-class staff/access administration surface, and policy such as `shift.close` is permanently bound to the manager role.

That is insufficient for the product requirement. Organizations must be able to decide whether cashiers, managers, or both may perform selected operational actions while preserving fail-closed server authorization, tenant isolation, auditability, and a simple cashier UX.

## Decision

### 1. Keep operational assignment roles unchanged

`pos_staff_location_assignments.role` remains:

- `cashier`
- `manager`

Do **not** add `admin`, `owner`, or `support` to this CHECK as a shortcut.

Cashier/manager describe **operational responsibility at a location**. They are not organization control-plane identities.

### 2. Add organization-level control-plane authority

Introduce a distinct server-owned organization membership/control-plane role:

- `owner` — highest tenant authority; may administer organization access and policy.
- `admin` — delegated organization administration subject to protected-owner restrictions.
- `support` — diagnostic/support access only where explicitly granted; no implicit commerce or staff-administration mutation authority.

A person may simultaneously be an organization admin and have an operational manager/cashier assignment. These are separate dimensions.

Browser/JWT self-declared role/capability is never authorization. The server loads current durable authority for each protected action.

### 3. Effective permissions are policy-resolved, not hard-coded UI claims

Keep named server permissions such as:

- `shift.open`
- `shift.close`
- `cash.movement`
- `cash.correction`
- `return.approve`
- `refund.resolve`

Add control-plane permissions for administration, for example:

- `admin.dashboard.read`
- `admin.staff.read`
- `admin.staff.manage`
- `admin.assignment.manage`
- `admin.location.manage`
- `admin.register.manage`
- `admin.device.manage`
- `admin.policy.manage`
- `admin.audit.read`
- `admin.diagnostics.read`

Effective operational permission is computed server-side from:

1. verified identity and organization;
2. durable organization control-plane membership where relevant;
3. durable location/register assignment;
4. operational role;
5. effective policy resolved by inheritance;
6. action context (own shift vs another staff member's shift, variance, register/location scope);
7. any explicit stronger-confirmation requirement.

### 4. Configurable operational policy

Policy inheritance:

`organization default -> location override -> register override`

The most specific defined value wins. Missing values inherit. Policy rows are POS operational truth and are auditable.

Initial shift-close policy must support at least:

- `cashierCanCloseShift: boolean`
- `managerCanCloseShift: boolean`
- `cashierOwnShiftOnly: boolean`
- `managerCanCloseOthersShift: boolean`
- `nonZeroVarianceRequiresManager: boolean`
- optional `varianceToleranceMinor` with currency

This allows:
- cashier only;
- manager only;
- cashier + manager;
- zero-variance cashier close with manager escalation for non-zero variance.

Default migration behavior must preserve current runtime semantics until an owner changes policy:
- cashier close: false
- manager close: true
- cashier own shift only: true
- manager close others: true
- non-zero variance requires manager: true

### 5. Separate Management control plane

Create a distinct role-gated Management area rather than expanding cashier Settings.

Initial navigation:

- Overview
- Staff & access
- Locations
- Registers
- Devices
- Shifts & cash
- Returns & approvals
- System health
- Audit
- Policies / settings

Cashier primary navigation remains focused on operational selling.

### 6. Diagnostics boundary

Engineering/support technical details, correlation IDs, build/contracts/local-schema diagnostics and privileged health data must not render in ordinary cashier/customer surfaces.

They belong in role-gated management/support diagnostics. Cashier-facing errors remain concise and actionable.

### 7. Mutation security and audit

All control-plane mutations require:
- authenticated staff/control-plane identity;
- current durable authorization;
- organization/scope verification;
- CSRF/origin protection;
- idempotency where effects require it;
- immutable/append-only audit event;
- no service-role credential in browser.

High-impact access changes may require explicit re-authentication/confirmation.

### 8. Staff identity lifecycle

The product must provide an authorized path for staff lifecycle management instead of routine manual Supabase work:

- list staff;
- invite/provision;
- disable/revoke access;
- assign operational role;
- assign locations/registers;
- view effective permissions.

Supabase Auth remains identity provider in the transition, but Auth user creation/disablement must be performed server-side through a privileged adapter, never directly from browser code.

## Rationale

Separating organization administration from location operations avoids turning `manager` into a global superuser and avoids inventing an `admin` operational role. Policy-resolved permissions support different retailers without forking authorization code, while server-side enforcement retains a stable permission vocabulary.

## Supersedes

Supersedes the assumption that `shift.close` must always be manager-only and the implicit product behavior where managers use only the ordinary cashier shell for all tasks.

Does not supersede:
- existing cashier/manager location assignment semantics;
- tenant isolation;
- server-owned authorization;
- CSRF/idempotency requirements;
- Woo/Supabase data ownership boundaries.

## Consequences

- `assignmentRolePermits()` becomes a baseline/default input, not the final authority for policy-controlled actions.
- A policy resolver is required before changing current behavior.
- Organization control-plane membership requires separate persistence.
- Management routes must fail closed for cashiers and unassigned users.
- Existing staging behavior remains unchanged until the policy resolver is integrated and configured.
- Historical runtime evidence remains valid for the SHA on which it was collected.

## Affected contracts

Internal authorization/control-plane contracts only initially. Frozen commerce wire contracts remain unchanged.

## Affected workstreams

WS3 owns authority model, persistence, BFF/server enforcement, audit and integration. WS1 may independently review/implement management presentation after foundation contracts stabilize. WS2 unchanged.

## pos-architecture-guardian

Result: PASS.

- canonical owner for POS staff policy/control-plane truth: Supabase POS operational store;
- identity provider remains Supabase Auth during transition;
- no duplicate commerce/pricing truth;
- no browser-owned authorization;
- organization admin role is distinct from operational cashier/manager role;
- policy inheritance is deterministic and tenant-scoped;
- production promotion remains separately gated.
